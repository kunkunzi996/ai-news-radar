# GitHub 重大更新筛选施工计划

## 本轮只做

- 实现满分 100、70 分展示的 GitHub 重大更新纯规则判定。
- 正式 Release 使用版本号与发布说明评分；预发布硬排除。
- 无 Release 时读取最新 commit 详情，用功能意图和产品代码证据评分。
- 新噪音不再进入归档，旧归档噪音不再进入读者数据；历史文件本身不删除。
- “没有重大更新”作为正常空结果，不显示成采集故障。

## 本轮不做

- 不改前端交互、GitHub 星标同步、取消订阅清理、部署、依赖或环境变量。
- 不删除、不批量重写 `data/archive.json`。
- 不使用大模型判断，也不增加用户配置项。

## 预计文件

- `scripts/radar/github_importance.py`：纯规则评分与旧归档兼容判断。
- `scripts/radar/fetchers/subscriptions.py`：Release 过滤、commit 详情读取与评分。
- `scripts/radar/cli.py`：生成读者数据时隐藏旧噪音，并记录正常空结果。
- `scripts/radar/server/common.py`：把“没有重大更新”识别为正常状态。
- `tests/test_github_importance.py`：评分规则边界测试。
- `tests/test_topic_filter.py`：GitHub fetcher 回归测试。
- `tests/test_local_server.py`：状态展示回归测试。
- `README.md`、`docs/SOURCE_COVERAGE.md`：同步实际行为。
- `PROJECT_STATE.md`：记录施工与验收状态。

## 施工顺序

1. 先写评分与 fetcher 的失败用例，确认旧实现会红。
2. 新增独立评分模块，让纯规则测试通过。
3. 接入 GitHub fetcher：Release 先筛选；无 Release 时补取 commit 详情。
4. 接入读者数据兼容过滤，保留原始历史归档。
5. 补正常空状态和相关回归用例。
6. 更新 README、信源说明与项目状态。
7. 运行 Python 专项、编译、差异检查和临时数据生成。
8. 使用浏览器检查重大更新可见、预发布和普通 commit 隐藏、其他订阅栏目不受影响。

## TEST_CHECKLIST

### 正常路径

- `2.0.0`、`6.2.0` 等正式主/次版本通过。
- patch/Calendar Version 的发布说明出现强功能信号时达到 70 分并通过。
- 无 Release 的 commit 同时具备强功能意图和产品代码证据时通过。

### 空输入 / 错误输入

- 空仓库返回正常空结果。
- 有 Release 但都不重要时返回“没有重大更新”，不回退普通 commit。
- commit 详情异常时保留现有上游失败语义，不伪装成功。

### 持久化检查

- 新的低置信度候选不写入归档。
- 旧归档记录不删除，只在读者数据中隐藏。

### 回归检查

- 稳定 repo/release/commit 身份、时间窗与去重逻辑保持不变。
- GitHub 空仓库和“没有重大更新”都不产生维护告警。
- 其他订阅来源的数量和展示逻辑不变。

### 边界情况

- `rc` 只按预发布字段、独立单词或版本后缀识别，不误伤普通单词。
- `feat` 单独出现不够；文档或测试改动即使行数很大也不能通过。
- 普通功能意图只有在新增模块或达到产品代码范围门槛时才能达到 70 分。

## 验收等级

- V1：专项单测、相关回归、`py_compile`、临时数据结构检查、`git diff --check`。
- V2：本地页面真实浏览器检查。
- V3：不需要。
