# GitHub 重大更新筛选设计

## 当前项目阶段

研发中期。GitHub 星标订阅与 Release/commit 采集已经上线，本轮只调整读者看到的 GitHub 更新质量。

## 背景

当前 GitHub 订阅会接纳所有非草稿 Release，包括预发布；仓库没有 Release 时还会回退到最新 commit。
真实归档中已有 303 条 GitHub 更新，其中 41 条为 commit 回退，存在 `update README`、自动同步、普通
Merge、格式整理和“反应测试”等噪音。用户希望宁可漏掉一些，也只展示高置信度的大版本或大功能更新。

## 已确认目标

- 只向读者展示高置信度的大版本或大功能更新。
- “大功能”必须同时具有明确功能意图和实质产品代码改动。
- 拿不准时默认隐藏，不为了凑数量降低门槛。
- 历史归档不删除；旧噪音只从展示结果中隐藏。

## 判定模型

新增一套独立的“GitHub 重大更新可信度分”，满分 100，展示阈值为 70。它只判断 GitHub 更新是否重大，
不复用现有新闻 `importance_score`；后者包含 AI 相关性、时效性和来源等级，业务含义不同。

### 硬排除

命中任一项直接隐藏，不参与评分：

- draft、prerelease、alpha、beta、rc、preview、nightly。
- 仅文档、测试、CI、格式、拼写、依赖、锁文件、自动同步或生成文件更新。
- 普通 Merge，且标题或变更内容没有可验证的大功能信息。

预发布优先使用 GitHub 的 `prerelease` 字段；从版本名补充判断时，只匹配独立单词或版本后缀，
不能因为普通单词中碰巧包含 `rc`、`beta` 等字母就误判。

### 正式 Release

- 标准语义化主版本（如 `2.0.0`）：100 分。
- 标准语义化次版本（如 `6.2.0`）：80 分。
- 其他正式版本：基础 25 分。
- 发布说明出现 breaking change、全新能力、新平台、新集成、核心重构等强功能信号：加 45 分。
- 发布说明出现普通新增功能、增加支持等信号：加 25 分。
- Calendar Version 或补丁版本不能只凭版本号过线，必须由发布说明补足证据。

### 无 Release 时的 commit

- `BREAKING CHANGE`、`feat!`、launch、introduce、全新平台等强意图：加 45 分。
- `feat`、新增功能、增加支持、接入新服务等普通功能意图：加 25 分。
- 确实修改了非文档、非测试、非 CI 的产品代码：加 25 分。
- 新增模块、命令、入口、平台或集成：加 20 分。
- 排除噪音文件后，修改至少 3 个产品代码文件或约 100 行：加 20 分。

commit 除了总分不低于 70，还必须至少包含一项“功能意图”证据和一项“产品代码”证据。
单独出现 `feat`、单独改动很多行、或单独新增文档都不能过线。
“产品代码”只统计排除 README、`docs/`、测试目录、`.github/`、锁文件和明显生成文件之后的源码；
配置文件单独变化不算产品代码证据，除非同时有明确的新平台或新集成功能意图。

## 数据流设计

1. Release API 响应已经包含发布说明，直接用于正式版本评分，不增加请求。
2. 无 Release 时先读取最新 commit；只有需要判断 commit 时，再读取该 commit 的详情，取得文件与改动统计。
3. 新候选在进入归档前执行重大更新门禁；低置信度候选不写入新的归档记录。
4. 生成读者数据时，对旧归档再执行兼容门禁；旧记录证据不足时保守隐藏，但原始归档保持不变。
5. 上游失败仍按失败记录，不把“没有重大更新”误报为采集错误。

## 模块边界

- 新增独立 GitHub 重大更新判定模块，只负责纯规则评分与可见性判断。
- GitHub fetcher 只负责取得 Release/commit 数据并调用判定模块。
- 数据管线只负责阻止低置信度候选入档，以及隐藏旧归档噪音。
- 不修改前端交互，不增加读者开关，不安装依赖，不修改部署或数据清理契约。

## 样本验收

应展示：

- `Partner 2.0.0`。
- `obra/superpowers v6.2.0`。
- `feat: 工具噪音过滤`，前提是 commit 详情证明修改了产品代码并达到 70 分。

应隐藏：

- `v1.4.164-rc.3`。
- `update README`。
- `chore(aihot): sync skill to v1.2.3`。
- `Merge pull request #17 from ...`。
- `新增：NanoGPT、kavel、反应测试`，如果实际只改名单或文档。
- `feat: streamline terminology lookup`，如果只是小范围调整、总分不足 70。

## 验收方式

- 单元测试覆盖 Release、commit、硬排除、70 分边界和历史兼容过滤。
- GitHub fetcher 测试覆盖无 Release 时的 commit 详情请求，以及高低置信度两条路径。
- 回归测试确认保留项目仍沿用稳定 repo/release/commit 身份和去重逻辑。
- 运行 GitHub 相关 Python 专项、Python 编译检查和 `git diff --check`。
- 生成一份临时数据并用浏览器检查：重大更新可见，预发布和普通 commit 不再出现，其他订阅栏目不受影响。

## 本轮不做

- 不删除或重写 `data/archive.json` 历史。
- 不使用大模型或外部付费服务判断重要性。
- 不增加页面设置项或手工白名单。
- 不改 GitHub 星标同步、取消订阅清理、API 契约、部署配置或依赖。
